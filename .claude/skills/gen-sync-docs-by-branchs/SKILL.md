# gen-sync-docs-by-branchs

## 概述

文件會過期。分支做完的事沒回頭改文件，下次讀文件的人（或 skill）就會照著錯誤狀態做決策。

本 skill 把**一個或多個 branch 的實際變更**，回寫到專案 docs 下的**發想／結構說明文件**（brainstorm、architecture 及同性質目錄），讓文件狀態與 codebase 對齊。

**本 skill 不預設任何專案的文件結構。** 目錄名、檔名、狀態標記慣例、項目編號，全部從當下 repo 現讀現解析。下面規範的是**方法**。

## 🔴 三條鐵律

### 1. 只依「實際 diff」寫，不依 commit message 寫

commit message 說做了什麼，diff 說**真的**做了什麼。兩者常有落差：宣稱完成但只做一半、順手改了沒寫進 message 的東西。**一律以 diff 為準。**

### 2. 找不到目標文件就停，絕不擴大搜索範圍

這是使用者明確指定的限制。在既定的文件目錄找不到對應的更新目標時：

- **詢問**使用者要更新哪份文件，或
- **終止**並回報「找不到目標文件」

**嚴禁**做以下事：
- 往 `docs/` 以外的目錄找（README、原始碼註解、wiki…）
- 把「已定案的規格／計畫」目錄（`features/`、`plans/`、`specs/`）當成備援目標
- 自己新建一份文件來「收容」找不到歸屬的變更

🔴 **本 skill 全程不跨出當前專案目錄。** 讀 diff、找文件、寫回檔案，全部在本 repo 內。不讀其他 repo 的分支、不查使用者家目錄的全域設定（`~/.claude`…）、不改專案外的任何檔案。使用者若指定專案外的 branch 或文件，回報無法處理並請他在該專案內執行本 skill。

### 3. 只改狀態與事實，不改決策

文件裡的取捨論證、否決理由、優先序排列，是經過討論的產物。本 skill 只更新「這件事做完了沒／做成什麼樣」，**不重排優先序、不復活已否決項目、不改寫設計理由**。有異議在輸出末尾建議。

## 執行步驟

### 1. 解析輸入的 branch

使用者可能給：branch 名稱（一或多個）、`current`／不指定（用當前分支）、PR 編號。

```bash
git branch --show-current
git branch -a --sort=-committerdate | head -20
```

**解析不出對應 branch 就停下來問**，不要猜相近的名字。

### 2. 取得每個 branch 的實際變更

先找 fork point，不要硬用 `origin/main`——分支可能從其他分支長出來：

```bash
BASE=$(git merge-base HEAD origin/main)   # 或使用者指定的 base
git diff --stat $BASE..<branch>
git log --oneline $BASE..<branch>
```

`--stat` 先看全貌抓出**受影響的模組**，再對關鍵檔案讀實際 diff。多個 branch 時逐一處理再合併結論，不要把 diff 混在一起看。

### 3. 定位目標文件目錄

**絕不寫死檔名。** 檔名常帶日期前綴，會新增、改名、合併。

慣例位置是 `docs/brainstorm/` 與 `docs/architecture/`：

```bash
ls docs/brainstorm/ docs/architecture/
```

不存在時（子專案、monorepo、命名不同）**在專案 docs 範圍內**搜尋：

```bash
find docs -maxdepth 2 -type d 2>/dev/null
```

⚠️ **搜索範圍僅限專案的文件目錄。** 這裡不存在就走鐵律 2（詢問或終止），不要往外找。

**排除已定案的規格／計畫目錄**（常見名稱：`features/`、`plans/`、`specs/`）——那是每個功能各一份的實作說明產物，不是本 skill 的更新對象。判準：**該目錄是「提案與結構說明」還是「已拍板的單次實作紀錄」**，前者才是目標。

### 4. 把 diff 對應到文件項目

對 diff 涉及的每個模組／功能，在目標目錄的文件裡找出**對應的項目**。用 `grep -n` 抓關鍵符號名、功能名、既有編號取行號，再用 `Read` 的 `offset`/`limit` 讀該區塊——文件動輒上千行，不要整份逐字讀。

要找的更新目標類型：

| 類型 | 常見形式 | 更新方式 |
|------|---------|---------|
| 完成度／狀態總表 | `⬜`/`🟡`/`✅` 表格、勾選清單 | 改狀態標記＋備註 |
| 項目本體描述 | 提案段落、設計方向 | 補上實際落地的形式與差異 |
| 結構說明 | 模組關係、資料流、目錄佈局 | 反映新增／移除／改名的元件 |
| 待辦清單 | Roadmap、下一步 | 已完成項目移出或標記完成 |

**沿用文件自己的編號慣例與狀態符號**，不要自創。

**對應不上時的處置**：

| 情況 | 動作 |
|------|------|
| 找到唯一對應項目 | 直接更新 |
| 找到多個候選 | 列出候選問使用者 |
| 完全找不到對應項目 | **不自行新增章節**——列出這筆變更，問使用者要放哪份／哪節，或標為「未歸檔變更」回報 |
| 整個目標目錄都不存在 | 走鐵律 2 |

### 5. 寫回文件

**最小 diff 原則。** 只改需要改的行，不順手重排版、不改無關文字、不「順便」修錯字。文件的 diff 要讓人一眼看出「哪個項目狀態變了」。

寫回內容應包含：

- **狀態標記**改成實況（用文件既有的符號體系）
- **一句實況備註**：實際做成什麼形式、與原提案的落差（若有）
- **不寫 commit SHA**——文件是給人讀的，SHA 過一陣子沒人查得動

### 6. 更新日期前綴與內文日期

這是使用者明確要求的一環。

**檔名日期前綴**：目標文件若採 `YYYY-MM-DD-<slug>.md` 形式，內容更新後**同步更新前綴為今天日期**。

```bash
git mv docs/brainstorm/2026-06-20-foo.md docs/brainstorm/2026-08-04-foo.md
```

⚠️ **必須用 `git mv`**（保留 rename 追蹤），並且**改名後要修正所有指向它的相對連結**：

```bash
rtk grep -rn "2026-06-20-foo" docs/
```

**內文日期標記**：文件內若有「（截至 YYYY-MM-DD）」「更新於 …」之類的標記，一併改成今天。

🔴 **今天的日期一律查 env context 的 "Today's date"**，不要用知識截止日期推算。

**不改名的情況**：檔名沒有日期前綴、或前綴語意是「建立日期」而非「更新日期」（從文件內文可判斷）時，保留原檔名，只更新內文日期標記。判斷不了就問。

### 7. 輸出摘要

改完後在 terminal 印一份摘要：

```
━━━ 文件同步摘要（branch: <name> → <today>） ━━━

【已更新】
  docs/brainstorm/2026-08-04-foo.md  （原 2026-06-20，已改名）
    · §D3 網路重送 ⬜ → ✅  實作為 RetryPolicy，與提案的 interceptor 形式不同
    · 完成度總覽日期 → 2026-08-04

【未歸檔變更】（找不到對應文件項目，需你指定去處）
  · <變更摘要> — 涉及 lib/src/xxx.dart

【建議】（未逕自修改）
  · <對排序或決策的異議，若有>
```

## 邊界

- **不 commit、不 push、不開 PR** — 只改檔案。要 commit 請接 `gen-commit`。
- **不擴大搜索範圍** — 見鐵律 2。找不到就問或停。
- **「專案」的定義** — 指本 skill 所在的 repo 根目錄（`git rev-parse --show-toplevel`）。session 若掛載了多個 working directory，只處理本 repo；其餘一律視為專案外。
- **不新建文件** — 本 skill 只更新既有文件。要新增發想文件請走 brainstorming 流程。
- **不改程式碼** — 只動 docs。
- **不改決策** — 見鐵律 3。
