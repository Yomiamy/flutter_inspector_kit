# gen-list-work-item-by-priority

## 概述

把散落在專案文件裡的待辦項目，彙整成一份**按優先序排列、且與 codebase 實況核對過**的清單，直接印在 terminal。

**本 skill 不預設任何專案的內容。** 待辦項目、編號慣例、優先序分層、技術棧，全部從當下 repo 的文件現讀現解析。下面規範的是**方法**，不是清單。

## 🔴 核心鐵律：文件狀態不可信，一律實查 codebase

**這是本 skill 存在的唯一理由。** 若只是把文件的待辦表格複述一次，使用者自己開檔案看更快。

腦力激盪／架構文件的狀態標記會與現實脫節，兩個方向都會發生：

- **標為待辦、實際已完成** — 做完沒回頭更新文件。直接複述會叫使用者去做已經做完的事。
- **標為完成、實際只做一半** — 元件建了但沒接線、函式定義了但零呼叫。
- **「重用既有零件」的估計不準** — 文件宣稱可重用的符號，可能是私有的、可能簽章接不上、可能根本不存在。這會讓 effort 估計整個失真。

**所以：每個要印出來的項目，都必須先實查 codebase 確認狀態。沒查過就不要印狀態。**

## 執行步驟

### 1. 定位來源目錄

**絕不寫死檔名。** 文件檔名常帶日期前綴，會隨時間新增、改名、合併。

慣例位置是 `docs/brainstorm/` 與 `docs/architecture/`：

```bash
ls docs/brainstorm/ docs/architecture/
```

不存在時（子專案、monorepo、目錄命名不同）**在專案的文件目錄範圍內**搜尋：

```bash
find docs -maxdepth 2 -type d 2>/dev/null
```

若專案的文件慣例確實不同（例如全部平放在 `docs/`），就用實際找到的目錄。

🔴 **搜索範圍僅限專案的文件目錄，絕不自行擴大。** 這裡找不到來源文件時，只有兩個選擇：

- **詢問**使用者要讀哪份文件，或
- **終止**並回報「找不到來源目錄」

**嚴禁**以下代償行為：
- 往 `docs/` 以外的目錄找待辦（README、原始碼 TODO 註解、GitHub issues、`~/.claude` 全域設定…）
- 退而求其次讀已定案的規格／計畫目錄（見下方排除規則）
- 自行從 codebase 推斷出一份待辦清單來頂替

> 註：搜索範圍的限制**全程適用**，不只這一步。步驟 4 的實查同樣只能在專案內進行，見該步驟。

**排除已定案的規格／計畫目錄**（常見名稱：`features/`、`plans/`、`specs/`）——那些是每個已完成功能各一份的產物，不是待辦來源，誤用會把已完成項目全列成待辦。判準：**該目錄是「提案與取捨」還是「已拍板的實作說明」**，前者才是來源。

### 2. 挑檔案並定位待辦區塊

取得實際清單後，用**檔名關鍵字**選檔，不要用日期猜。同一主題命中多份時全部讀，以**日期最新者為準**，舊檔只補新檔省略的細節（文件常有合併歷史，最新那份通常已含完整脈絡）。

文件動輒數百上千行，不要整份逐字讀。先 `grep -n` 抓標題取行號，再用 `Read` 的 `offset`/`limit` 讀該區塊。要找的標題類型：

| 區塊類型 | 常見標題關鍵字 | 用途 |
|---------|--------------|------|
| 主清單 | 優先順序總表、優先序建議、Roadmap | 已排序的項目本體 |
| 最新排序決策 | 下一步實作路徑、Tier、Phase | **優先於主清單**——主清單可能是舊排序 |
| 提案本體 | 提案、改善方向、缺口分析 | 取 effort／價值／影響範圍 |
| 狀態總覽 | 完成度總覽、現況盤點 | 只作對照，**狀態欄一律不可信** |

**先辨識該專案的項目編號慣例**（`§D*`／`§P*`、`#N`、`RFC-N`…都可能），後續全程沿用文件自己的編號，不要自創。

### 3. 篩掉已否決的項目

文件通常含大量**明確否決／不排程／降級**的項目，且**否決理由往往比提案本身更長**——那是經過論證的決策，不是待辦。

辨識標記：`❌`、`已否決`、`不排程`、`降級`、`Anti-features`、刪節線標題。

**這些不列入優先序清單**，僅在輸出末尾以單獨區塊列出標題與一句理由摘要，讓使用者知道「這些被想過且被拒絕了」，避免下次重提。

### 4. 實查每個候選項目的真實狀態

對每個候選項目，從文件的「設計方向／影響範圍」段落取出它的**必要產物**（新類別、新函式、新欄位、新腳本、新設定鍵），然後查該產物在 codebase 是否存在。

**查法原則：以「符號名 + 整個原始碼根目錄」為準，不綁定單一檔案路徑。** 檔案會被重構搬走，綁路徑的查法會在搬動後誤報「未實作」：

```bash
# 通用形式：<符號> 換成文件裡該項目的必要產物名稱
grep -rln "<符號A>\|<符號B>" <原始碼根目錄>
```

原始碼根目錄依專案而定（`lib/`、`src/`、`app/`…），先確認再查。

**若項目屬於工具／腳本／skill 類**（非產品原始碼），先動態定位其在**專案內**的安裝位置再查，不要假設固定路徑：

```bash
find . -name "<入口檔名>" -path "*<工具名>*" -not -path "*/.git/*" 2>/dev/null | head -1
```

🔴 **搜索範圍僅限本專案，絕不跨到專案外。** 不查使用者家目錄的全域設定（`~/.claude`、`~/.config`…）、不查其他 repo、不查系統安裝路徑。

專案內查無時標「**無法驗證**」，**不要標成「未實作」**——該產物可能安裝在專案外的全域位置，本 skill 不越界查證，所以無從斷定。輸出時明確標示，讓使用者自行判斷是否需手動確認。

**判定規則**：

| 實查結果 | 判定 | 動作 |
|---------|------|------|
| 查無產物 | 待辦 | 列入清單 |
| 查有產物且位置正確 | 已完成 | 不列入；文件若仍標待辦 → 進「文件與實況不符」 |
| 命中但位置／形式不符需求 | 部分完成 | 列入，備註實際缺口 |
| 產物疑似裝在專案外（本 skill 不越界查） | 無法驗證 | 列入但標「無法驗證」，**不得標為未實作** |

**⚠️ 命中 ≠ 完成。** 同名符號可能出現在無關檔案；元件可能存在卻從未被呼叫；某個類別可能是私有持有、正是該項目要重構的對象。**命中後必須確認它落在該項目要求的位置與形式**，否則會把待辦誤判為完成。同理，`grep -rl` 可能回傳多個檔案，逐檔查而非塞進命令替換（會因空白切分而壞掉）。

> 用 `rtk grep` 節省 token。若 rtk 折疊輸出導致看不到行內容，改用 `dangerouslyDisableSandbox: true` 跑原生 `grep`。

### 5. 排序

**主排序：沿用文件既有的 Tier／Phase／優先序。** 這些順序通常是文件經反覆論證得出的（項目被升降級往往附有整段理由）。**不要自行重排**——若你認為某項該調整順位，在輸出末尾建議，不要逕自改動。

**次排序（同層級內）**：

1. **綁定相依優先** — 文件若寫明「A 必須排在 B 之前」，嚴格遵守
2. **既有缺陷 > 新功能** — 侵蝕既有功能可信度的 bug 優先
3. **價值降序**（文件若有 ⭐ 或等級標註）
4. **Effort 升序**

**分區塊**：若文件涵蓋多條產品線（如產品原始碼 vs 開發工具鏈），**各自排序不混排**——執行者、驗證方式、風險面都不同。

### 6. 輸出

直接印在 terminal（不寫檔）。骨架如下，**分層名稱用文件實際使用的**（Tier／Phase／優先序皆可）：

```
━━━ 待辦項目優先序清單（實查於 YYYY-MM-DD） ━━━

【A. <產品線名稱>】

  <文件的分層名> · <該層意義>
   1. <文件編號>  <標題>                      [effort] <價值>
      └ 實查：<查了什麼、結果如何>
      └ 寫入：<影響範圍檔案>
      └ ⚠️ <文件估計與實況的落差，若有>
   ...

【B. <另一產品線>】
   ...

━━━ ⚠️ 文件與實況不符（建議回頭修文件） ━━━
  · <項目>：文件標為 X，實查為 Y

━━━ 已排除（否決／不排程，非待辦）━━━
  <編號> <標題> ❌ <一句理由>

━━━ 實查途中發現（非文件項目）━━━
  · <僅在有發現時才出現此區塊>
```

每項固定含：**編號 → 標題 → [Effort] → 價值 → 實查證據 → 寫入路徑**。

**實查證據不可省略**——那是這份清單與直接讀文件的唯一差別。

### 7. 動工前提醒

輸出末尾附一句提醒：

> 標為 trivial／low 的項目，動工前先 grep 一次「這個判斷在幾個地方被重寫過」。低估通常不在「要寫的新程式碼」，而在「動到的既有判定有幾份、是否已漂移」。

若文件本身記載過類似的 effort 估計偏差教訓，改引用該專案自己的實例，更有說服力。

## 邊界

- **只列不做** — 不動程式碼、不建 issue、不開分支。要動工請接該專案的開發流程 skill。
- **🔴 全程不跨出專案目錄** — 文件來源（步驟 1）與 codebase 實查（步驟 4）都只在本專案內進行。不查 `~/.claude` 等家目錄全域設定、不查其他 repo、不查系統路徑。文件找不到就詢問或終止；產物查無就標「無法驗證」。
- **「專案」的定義** — 指本 skill 所在的 repo 根目錄（`git rev-parse --show-toplevel`）。session 若掛載了多個 working directory，只處理本 repo；其餘一律視為專案外。
- **不寫檔** — 只印 terminal。使用者要存檔會自己說。
- **不自創項目** — 清單只能來自文件既有項目。實查途中發現的新問題另起「實查途中發現」區塊，明確標示非文件項目，不混進優先序表。
- **不推翻文件決策** — 已否決項目不因你覺得有價值就復活；排序有疑慮用建議的方式提出。
