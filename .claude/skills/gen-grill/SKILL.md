# 需求盤問閘門 (gen-grill)

在最強推論（planner / opus / xhigh）花成本寫出整份規格**之前**，先確認需求本身沒歪。

方向錯的規格，代價不只是重寫一份文件——STAGE 0b 的計畫、STAGE 2 的實作全部建在上面。愈晚發現愈貴。

問法對齊上游 [`mattpocock/skills` 的 `grilling`](https://github.com/mattpocock/skills/blob/main/skills/productivity/grilling/SKILL.md)（`grill-me` 即其薄包裝）：決策樹 + 逐輪 frontier + 推薦答案 + 事實自查 + 結束確認。本 repo 在其上加了三樣東西：**Q1–Q5 根節點**、**Q5 必跑**、**短路條件**。

## 🔴 本 skill 不產生任何文件

唯一產出是 brief——**一段印在對話裡的結構化文字，不落檔**。不論是 STAGE 0·grill 自動觸發、使用者單獨打 `/gen-grill`、還是 quick 模式，都一樣。

文件一律由後面兩個 stage 產出：`docs/features/`（STAGE 0a）與 `docs/plans/`（STAGE 0b）。盤問階段**不寫檔、不寫規格、不寫計畫**。

### 與 `brainstorming` 的邊界

**本 skill 不呼叫 `brainstorming`。** 該 skill 的流程是有序的——提問之後強制「提出 2-3 個方案 → 展示設計逐節取得批准 → 寫設計文件 → 使用者審閱 → 呼叫 `writing-plans`」，其明訂終態是 `writing-plans`，不會回到呼叫端。若呼叫它，會在 STAGE 0a 之前就產出設計文件與實作計畫，與 `docs/features/`、`docs/plans/` 重複，且不會回來產 brief。

| | 職責 | 終態 |
|:---|:---|:---|
| **`gen-grill`**（本 skill） | 盤問需求到理解一致 | 回傳 brief 給 planner |
| **`brainstorming`** | 完整設計流程（提問 → 方案 → 設計 → 文件） | `writing-plans` |

## 決策樹：以 Q1–Q5 為根

把需求建模成**決策樹**：每個決策底下掛著由它衍生的子決策。本 skill 的樹固定從下列五個根節點長出——它們保證這五個面向一定被問到，但**不是填完就走的表單**：根節點答完，由答案衍生出的子決策同樣要問。

| # | 根節點 | 已確定 | 未確定 |
|:-:|:---|:---|:---|
| **Q1** | 問題定義 | 說得出**要解決的具體問題**：誰在什麼情況下卡住、現況會怎樣 | 只說「想要 X 功能」——那是解法不是問題 |
| **Q2** | 觸發場景 | 說得出**至少一個具體場景**：什麼人、什麼操作、什麼前提下會遇到 | 「使用者可能會需要」這類假想需求 |
| **Q3** | 成功標準 | 說得出**可驗證的完成樣子**：做完後拿什麼判斷對不對 | 「更好用」「更清楚」這類無法證偽的敘述 |
| **Q4** | 範圍邊界 | 說得出**明確不做什麼**，尤其是相鄰、容易順手做掉的部分 | 完全沒有邊界，或只說「先做基本的」 |
| **Q5** | 既有覆蓋 | **已實查 codebase**：確認要做的東西不存在、或存在但不符需求，並附證據（符號 grep 結果 / 檔案路徑 / 行號） | 只憑文件敘述或印象判斷「這個還沒做」 |

**樹的深度止於需求層。** 資料結構、API 形狀、檔案落點等**設計決策**是 STAGE 0a planner 與 STAGE 0b plan-verifier 的職責；盤問中冒出這類分支時，不在此展開，記進 brief 的「留給 planner 的開放問題」。

## 盤問方式：逐輪問完 frontier

**frontier** = 所有前提都已確定的決策——也就是現在就能問、不必猜使用者還沒給的答案的那些問題。

1. **一輪問完整個 frontier**，每題編號並附上你的推薦答案，然後**等使用者答完**再進下一輪。
2. 同一輪內的問題**彼此不得相依**：答案取決於本輪另一題的問題，屬於下一輪。
3. 每輪答完後重算 frontier：已確定的決策把 frontier 往外推，解鎖依賴它們的問題。
4. 使用者指出某個答案應該改變先前的決策時，重開受影響的分支，於下一輪再問。

每輪格式：

```
❓ **Q1** - **<問題標題>**：<問題內容，可多段，可含選項>

➡️ <你的推薦答案>

---

❓ **Q2** - **<問題標題>**：<問題內容>

➡️ <你的推薦答案>
```

措辭讓「是」等於接受你的推薦答案。使用者可以照編號批次回覆（「1 是、2 選第二個、3 不，因為……」）。

### 事實自己查，決策交給使用者

**找事實是你的工作，不是使用者的。** frontier 上的問題需要環境裡查得到的事實（檔案、符號、git 歷史、issue 內容）時，派 subagent 去查，**不要拿來問使用者**。

查詢不阻塞整輪：進行中的查詢視為未確定的前提，只有依賴它的問題等它回報，frontier 其餘問題照問。

**Q5 本身就是事實**，一律自己查（派 subagent 或直接 grep），**不問使用者**。通常可在第一輪開問的同時就派出去。

**決策屬於使用者**：逐一交給使用者並等待回答。自己替使用者回答決策，等於這次盤問失效。

## 結束：frontier 清空 + 使用者確認

frontier 清空 = 決策樹每個分支都走過、沒有任何東西被默默假設。此時：

1. 印出 brief 草稿（格式見下）。
2. **請使用者確認雙方理解一致**，確認前**不交給 planner**。使用者有修正就回到盤問。

題數不設上限——有的需求三題、有的五十題。使用者說「收斂吧」「夠了」時，以當下狀態產出 brief，未確定的分支列進「留給 planner 的開放問題」。

### 為什麼有 Q5（本 repo 專屬，上游沒有）

因為本 repo 最大的 misalignment 來源不是「需求沒講清楚」，是**文件與實況漂移**：

- **§D4**（Issue #159）：照文件字面做完、610 tests 全綠，才發現落點錯一層且漏了核心需求，**整案棄發 PR**
- **本 skill 自己**（Issue #166）：文件稱 `brainstorming` 缺一問一答，實查證偽——機制早已存在
- **§P8 / §D6 / §P19**：三次標為待辦、實查已完成

Q5 花的是幾次 grep 的時間，擋的是整輪白工。

## 短路條件（跳過 Q1–Q4 的盤問）

符合任一項即跳過 Q1–Q4——盤問本身有成本，對已經清楚的需求施加摩擦會重演「人在迴路頻率過高」的老問題。

- **已有文件背書**：`docs/features/` 或 `docs/plans/` 已有對應規格或計畫
- **已 triage 的 issue**：需求帶 `#編號`，且 issue body 已含驗收條件
- **機械性改動**：改版號、修 typo、照既有表格逐項執行等，做法本身無歧義
- **quick 模式**：見下

> 短路只跳過 Q1–Q4。**Q5 一律要跑**——前三次漂移全發生在「看起來已有文件背書」的項目上，正是短路最容易放過的那一類。
>
> 短路時沒有盤問輪次，也不需要結束確認——直接產出 brief（Q5 照填）。

## quick 模式行為

`quick` 是小修正通道，全套盤問與它的定位衝突。

**quick 模式下只跑 Q5（既有覆蓋實查），Q1–Q4 略過。**

理由：quick 處理的是描述已足夠具體的小改動（Q1–Q4 天然齊備），但「這個是不是已經做過了」跟改動大小無關——`§P8` 當初就是個 trivial 項目，實查才發現早已完成。

## 產出：brief 交接格式

使用者確認後（或短路／quick 時直接）產出下列結構，交給 planner 作為 STAGE 0a 的輸入：

```markdown
## 需求 brief（gen-grill 產出）

**Q1 問題定義**：<要解決的具體問題>
**Q2 觸發場景**：<誰、什麼操作、什麼前提>
**Q3 成功標準**：<可驗證的完成樣子>
**Q4 範圍邊界**：<明確不做什麼>
**Q5 既有覆蓋實查**：
  - 查了什麼：<符號 / 檔案 / 文件>
  - 結果：<未實作 / 部分完成，缺 X / 已完成但不符需求，因為 Y>
  - 證據：<grep 結果、file:line>

**盤問中確定的其他決策**：<子決策與答案；無則寫「無」>
**留給 planner 的開放問題**：<設計層分支、使用者喊停時未確定的分支；無則寫「無」>

**放行方式**：使用者確認 ｜ 短路（<哪一條>）｜ quick 模式
**盤問輪數**：<N>（短路時為 0）
```

planner 依此 brief 撰寫規格，不需再重新釐清需求。

**若 Q5 的實查結果與原始需求敘述衝突**（例如「文件說沒做，實查發現已完成」），**先回報使用者再繼續**——這種情況下需求本身可能要重新定義，不是往下寫規格的時機。

## 完成條件

- 一般路徑：frontier 清空（或使用者喊停）、使用者確認理解一致、brief 已交給 planner。
- 短路／quick：Q5 已跑、brief 已交給 planner。
